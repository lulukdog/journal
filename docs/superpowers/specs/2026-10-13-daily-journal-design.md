## 1. 意图

做一个随身的东西。你随时可以跟它说一句——工作的间隙、地铁上、吃饭的时候——说今天发生了什么、你在想什么，偶尔拍张照片。它安静地收着，不打断你。

它跟普通日记 App 的根本区别是：**它不是等你去写，它会在攒够东西之后回过头来找你。** 当它认为有话说的时候，它会开口；当你明确问它的时候，它必须回答。你要的不是一个记录工具，是一个记得你、并且偶尔给你判断的东西。

这条产品的成败，九成取决于**它什么时候开口、开口说什么**，而不是它能聊多好。

---

## 2. 目标 / 非目标 / 反目标

### 目标

1. **随手就能记。** 打开就说话，中间没有表单、没有分类、没有选心情。手和注意力被占着的时候也能用。
2. **它会积累。** 原始记录 → 每天的卡片 → 周/月趋势 → 一份关于"你是谁、你现在什么处境"的画像。
3. **它默认闭嘴，但有话说的时候会说。** 记录是默认动作，回应是例外。
4. **每天有一张「今天的你」。** 这是承诺，雷打不动，不算它"开口"——所以打开 App 永远不会是空的。
5. **明确提问时必须回答。** 你说"我该怎么做"，它就得给你分析，不能只记录。
6. **它有话想说是存着的。** 第一版**不做推送**（用户决定：先不推送，自己点开看）。它想说的话存在那儿，等你下次打开时出现在流的最上方。

### 非目标

- 不做社交、不做分享、不做多用户。第一版只有你一个人用。
- 不做语音转写。语音走手机输入法的听写功能。
- 不做本地模型。已决定用零一万物云端 API。
- 不做独立的"对话窗口"。所有事情在一个窗口里解决。
- 第一版不做原生 App、不上架。
- 不做心理诊断。见 5.6。

### 反目标 —— 什么算失败，即使它能跑

1. **它理解错了你的情况，还下了断言。** 这是最不可忍的一条。宁可不说话，也不要猜错了还说得很确定。
2. **你只想倾诉的时候它给你上课。** 这是这类产品最典型的死法。
3. **它每天说一样的话。** 模板化的、空洞的关心，比不说话更糟。
4. **它的主动开口变成噪音。** 一旦你开始忽略它的消息，这个产品就已经死了——而且很难救回来。
5. **记录变成负担。** 一旦你因为"今天还没写"而产生压力，就会开始逃避，然后卸载。
6. **三个月后回看，什么都看不出来。** 攒了一堆流水，但没有形成任何有意义的东西。

## 4. 已经定下来的事（用户决定）

| 项 | 决定 | 理由 |
|---|---|---|
| 平台 | Web（不是小程序，不是原生 App） | 小程序的"订阅消息"模型给不了无限期的主动推送，会在最核心的需求上废掉 |
| 界面 | 一个窗口 =「流 + 每天的卡片」 | 一天是一个单位；回看、心情、主动找你都需要"一天"这个概念存在 |
| 输入 | 打字为主，语音用手机输入法听写 | 用户自己提的，绕开了整套 ASR 管道 |
| 模型 | 零一万物云端 | 优先判断质量。本地模型试过论证，判断力不够 |
| 隐私 | 接受记录离开本机，存在自己的服务器上 | 不用公司服务器 |
| 它开口的方式 | **先问，再下判断** | 猜错了代价不对称 |
| 部署 | 用户自己的阿里云服务器 | 7×24 在线 + 外网可达 |

## 5. 具体设计

### 5.1 数据模型

六张表。**关键在于 `memories` 和 `entries` 是分开的**——这是整个产品能不能在第 4 条诉求上成立的分水岭。

```
entries      一条原始记录。id, ts, kind(text/image), content, image_path, day
days         每天的卡片。date, entry_count, mood(-2..2), mood_label, headline, state
summaries    周/月总结。period_type, period_key, content, metrics
memories     关于"你是谁"的稳定事实。key, value, confidence, first_seen, last_seen, status
utterances   它说过的话。id, ts, trigger, content, delivered_via, user_reaction
events       可审计的信号记录（用于判断"有必要"）。id, ts, signal_type, payload, resolved
```

**为什么 memories 必须独立**：`entries` 是流水，会无限增长，而且大部分是噪音。你问"我该不该辞职"，需要的是"他的收入结构是什么、家里有什么负担、他自己说过最在意什么"——这些是有限条数、会被更新和推翻的**事实**，不是一堆原始句子。把所有 entries 塞进上下文既贵又不准，几周后必然崩。

### 5.2 记忆分层

| 层 | 内容 | 什么时候生成 | 怎么用 |
|---|---|---|---|
| L0 | 原始 entry | 你说的时候 | 全文检索 |
| L1 | 当天的卡片 | 当天滚动更新 + 每晚收口 | 回看、趋势 |
| L2 | 周/月总结 | 每周一 / 每月 1 号 | 长程趋势 |
| L3 | 画像（memories） | 有新材料时增量更新 | 回答"我该怎么做" |

**检索**：第一版用 SQLite 自带的 FTS5 + `trigram` 分词器做中文全文检索，**不上向量检索**。理由：一年也就几千条记录，关键词 + 时间范围足够；向量检索要多一个 embedding 服务、多一份成本和不确定性，现在不值得。数据量到几万条再说。

**喂给模型的上下文构造**（每次对话时拼）：
1. L3 画像全量（这个不大，几百到一两千字）
2. 最近 7 天的卡片
3. 检索到的相关原始 entries（最多 N 条，按时间倒序）
4. 最近若干条它说过的话（避免重复说同样的话）

**L3 画像怎么更新**：每天卡片收口之后，紧接着跑一次「事实抽取」——把当天出现的新事实合并进 `memories`（新的插入，冲突的更新并降权旧的，长期没被提到的降低 confidence 但**不删除**，因为"他曾经这么想"本身是信息）。

**记录永远不依赖模型**：你说的话先落 SQLite，再去调模型。API 挂了、限流了、欠费了，记录照样存得住，`entries` 的 `processed` 标记为 false，下次补跑。这条是硬要求——记录功能失效比它说错话更致命。

### 5.3 它什么时候开口（核心）

三个触发源，优先级从高到低：

**A. 你明确提问 → 必须回答。**
交互上用一个明确的动作来区分，**不依赖语义判断**。见 5.7。

**B. 每天一次「今天的你」→ 固定承诺。**
不是"开口"，是记录的一部分。

**C. 它自己判断有必要 → 例外。**
这一条必须建立在**可执行、可审计的规则**上，而不是"让模型自己觉得"。每条触发都写进 `events` 表，事后能查"它为什么在那天找我"。

第一版实现这六条信号：

| 信号 | 判据 | 为什么 |
|---|---|---|
| 重复 | 同一主题/情绪在 N 天内出现 M 次 | 最可靠的信号。反复出现的东西才是真的 |
| 落差 | 最近 7 天心情均值和之前 30 天偏离超过阈值 | 变化比绝对值重要 |
| 悬置 | 提过一个决定或日期，超过 X 天没有下文 | 人在回避什么，往往是重要的 |
| 临近 | 他提过的时间点快到了 | 这个最有价值，也最不容易误判 |
| 沉默 | 连续 N 天没说话 | **要非常小心**，见下 |
| 风险 | 出现明确的自伤/极端表达 | 单独处理，见 5.6 |

**沉默信号的特殊处理**：连续没说话**不一定是坏事**——可能只是不需要。所以这条触发**不产生断言，只产生一句极轻的招呼**，而且频率上限很低（比如最多每 7 天一次），并且如果被忽略两次就自动停用一段时间。误判的代价不对称，这里必须保守。

**运行节奏**：所有信号检测在每晚卡片收口（23:30）之后紧接着跑一次。检测到的话，就写进 `utterances`，**等你下次打开 App 时出现在流的最上方**。

**为什么信号检测只跑一次**：白天新增的记录会先更新当天卡片，但不会即时触发信号判断。否则「重复」这类信号会在一天里被反复触发。**一次一天，是个刻意设的上限。**

### 5.4 它开口的形态：先问，再判断

当信号 C 触发时，它**不直接给分析**。流程是：

```
信号触发
  → 它生成一句「低承诺的观察或询问」
     （例："你这几天提了好几次累，是我读错了吗？"）
  → 你回应
  → 只有在你确认之后，才进入分析、建议、追问
```

理由：猜错了，问一句的成本只是一句多余的关心；直接下判断，猜错了就是反目标第 1 条，是你会卸载它的那种事。

**「低承诺」的意思是**：它可以指出它观察到的**具体事实**（"你这三天说了四次累"），但不下结论（不说"你状态不好"、不说"你压力很大"）。

### 5.5 每天那张卡片

- **一天的边界**：凌晨 4:00 到次日 4:00。理由：半夜说的话应该算前一天。
- **滚动生成**：每有一条新记录就增量更新当天的卡片，不是等到晚上才生成。所以白天打开也能看到当前状态。
- **每晚收口**：23:30 跑一次 job，把当天定稿。
- **卡片内容**：条目数、图片数、状态条、一句话概括、当天的关键词。
- **状态分 `mood`**：-2 到 +2。**只用于画状态条和看趋势，不展示成"评估结果"。** 标签用你自己的词（"有点钝，但还没塌"），不用"焦虑/抑郁"这类临床词。

### 5.6 关于"防止抑郁"这条诉求（重要）

用户提出希望它"评估心理状态、防止抑郁"。**这一条我要明确收窄，因为做过头会伤人。**

它**不做**：
- 不做心理诊断，不给"抑郁风险评分"
- 不推送"你可能有抑郁倾向"这类话
- 不因为几天的低状态就下结论
- 不说教，不说"你应该多运动/多社交"

它**做**：
- 描述它观察到的具体事实，不下判断
- 在出现**明确的自伤或极端表达**时，给一个温和的、不评判的回应，并指向真实可及的帮助（人，不是产品）
- 把这个约定写进系统提示词，并且**用规则兜底**（关键词检测独立于模型判断）

理由：一个日记 App 说错"你有抑郁风险"，比不说更糟——它可能吓到你，也可能给你虚假的安心。这类判断应该交给人。

### 5.7 界面与交互

一个页面，从上到下：

```
┌─────────────────────────┐
│  7 月 14 日 · 周一        │  ← 日期，可左右滑/点击切天
├─────────────────────────┤
│  ┌───────────────────┐  │
│  │ 今天的你           │  │  ← 卡片：几段、几条状态、
│  │ 5 段 · 2 图        │  │     一句话概括
│  │ ▓▓▓▓▓             │  │     点开看当天全部
│  │ "有点钝，但还没塌"  │  │
│  └───────────────────┘  │
├─────────────────────────┤
│          今天又要开会 →  │  ← 流：你的记录
│          午饭没胃口   →  │
│  ← 你这几天提了好几次累  │  ← 它的话（插在流里）
│          再撑撑看吧   →  │
├─────────────────────────┤
│ [说点什么…        ] [📷] │
│ [ 记一笔 ] [ 问它 ]      │  ← 两个按钮，明确区分
└─────────────────────────┘
```

**核心交互决定：用两个按钮区分「陈述」和「提问」，不用语义判断。**

- 左「记一笔」= 只记录，它默认不回应（除非信号 C 触发）
- 右「问它」= 必须回答
- 键盘回车 = 「记一笔」（默认动作是记录）
- 发完消息后，那条记录上仍有一个「问它」的小按钮，可以事后补问

理由：纯语义判断一定会误判，而误判的代价不对称（见反目标 1）。一个明确的按钮，用户多花半秒，但永远不会错。

**图片**：右下角相机按钮，调系统相机或相册。图片存服务器本地磁盘 `/var/lib/journal/media/YYYY/MM/`，路径写进 `entries.image_path`。

传给模型时按 OpenAI 兼容格式转成 base64 data URL 塞进 message 的 `image_url` 字段。**上传前在浏览器端先压到长边 1568px 以内**——一是省流量（你在手机上，可能是流量），二是省 token（大图会被切块，费用按块算），三是避免超过请求体上限。原始图仍然原样存在服务器上，压过的只是发给模型的那份。

**图片不限量**，当天的照片全部发过去。也不做「模型不收图片就去掉图片重试」的降级：静默降级是最坏的，模型哪天开始读不懂照片你永远发现不了，宁可让它报错。

**历史**：卡片可以往回翻，点开某天能看到当天全部原始记录。这是"三个月后还能翻回去"的落点。

### 5.8 推送（第一版不做）与安全

#### 推送

**第一版不做推送。** 用户明确决定：先不推送，自己点开看。

这简化了不少东西：不要飞书集成、不要外部服务、不要管浏览器推送的平台限制，也多一个隐私出口都不需要。

**代价要说清楚**：没有推送，「它主动找你」就退化成「你下次打开才看到」。所以：
- 信号里的「**临近**」会失效——它本来是用来提醒你「你提过的那件事快到了」，但等你打开的时候可能已经过了。这条信号第一版保留检测、但不指望它有用。
- 你原始需求里的第 6 条（「每天推送看一下心情状态」）现在没有了。它变成了一张你打开才看到的卡片。**这是有意为之，不是遗漏。**

推送推到第二版。到时候的选项：飞书群自定义机器人 webhook（最省事，你已经打通了）、或手机浏览器/PWA 的 Web Push（iOS 上要求「添加到主屏幕」且不稳）、或自建应用 bot。

#### 安全（一个真实的妥协）

没有域名 = 没有 HTTPS。这意味着**你的日记从手机到服务器的路上是明文的**，在别人家的 WiFi 或某些链路上可能被看到。这是真实的弱点，我不打算掩饰。

第一版的缓解：
- 登录用一个长随机口令，登录后写 HttpOnly + SameSite=Lax 的 cookie
- 服务器 ufw 只开 22 和 10002
- 应用层加限流，防止口令被暴力破解

第一版**明确不做**的：
- HTTPS（没有域名）
- 改 root 密码（用户明确决定保持现状）—— **这个风险记录在案**：root + 弱口令 + 公网 22 端口，是全自动爆破的首要目标。

**下一步的安全升级选项**（不在第一版）：
- **Tailscale**：服务器和手机组成私有网络，端口完全不用对公网开放，同时拿到 WireGuard 层的加密。代价是手机要装并常开一个 App。
- 买域名 + ICP 备案 + Let's Encrypt：最正规，但备案流程很长。

第一版不做的理由：这个产品的第一条命是"随时能用"。为了安全引入一个额外的常驻依赖，会先伤到核心诉求。

### 5.9 冷启动（第一批素材）

**从零开始积累是这类产品最容易死的地方**——用户第三天打开发现它什么都不知道，就走了。

所以第一次打开时走一个**引导访谈**：它一次问一个问题，你可以跳过任何一个。

问题清单（不一次性列出，逐个问）：
1. 你现在靠什么生活？（收入来源、大概的量级）
2. 每个月大概要花多少？手上有多少能撑多久？（可以给区间，不用精确）
3. 家里有谁需要你照顾？有什么固定负担？
4. 你现在最在意的一件事是什么？
5. 你最近一次觉得"这样不行"是什么时候？
6. 你希望我怎么跟你说话？（直接一点 / 温和一点）

答案直接写进 `memories`，成为 L3 画像的第一批内容。**只有答完这个，它才有资格在信号 C 上开口**——在此之前，触发规则里的"落差""悬置"都没有基线，判断不了。

## 6. 技术选型与部署

### 选型

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **Python 3.10**（服务器已装） | 不引入新运行时。内存紧，少一个东西少一份风险 |
| Web | **FastAPI + uvicorn** | 异步调用 LLM API；依赖少 |
| 数据库 | **SQLite**（单文件，stdlib） | **1.7 GB 内存决定了不能用 Postgres** |
| 检索 | SQLite FTS5 + trigram | 中文可用，零额外依赖 |
| 前端 | 单个 HTML + 原生 JS + CSS | 没有构建步骤，没有 npm，服务器上不需要 Node |
| 进程 | systemd unit | 开机自启、崩溃重启，不用 Docker（Docker 自身要 200MB+） |
| 定时 | systemd timer | 每晚收口卡片、跑信号检测 |
| 反向代理 | **不用 nginx** | 直接 uvicorn 监听 10002，省内存省复杂度 |

**模型分工**：默认全部走 `deepseek-v4.1-flash`（100 万上下文，支持图片，够便宜）。「问它」这类需要深度推理的调用允许切到 `gpt-5.6-luna`——**把它做成一个配置项，不要在代码里写死**，因为你会在用了几周之后才真正知道哪个更合适。

**已经确认的环境事实**（实测过，不用再查）：
- 服务器时区已经是 `Asia/Shanghai`，不需要改。一天的边界 4:00 直接按本地时间算。
- 服务器到 `openapi.lingyiwanwu.net` 通（返回 403，说明只是缺鉴权）。
- 服务器到 `open.feishu.cn` 通。
- 内存 1736 MB，空闲 1090 MB，swap 4 GB 已开。

### 部署

- 端口：**10002**（安全组 10000–10010 已开放）
- 代码位置：服务器 `/opt/journal`
- 数据位置：服务器 `/var/lib/journal/journal.db`（单文件 SQLite）+ `/var/lib/journal/media/`（图片）
- 密钥：零一万物的 API key 走 systemd 的 `EnvironmentFile`，不写进代码库
- 备份：第一版做一个每晚把 db 复制到 `/var/lib/journal/backups/` 的 job（同一个磁盘，只防误删，不防机器挂）
- 部署方式：本地开发 → `rsync` 到服务器 `/opt/journal` → `systemctl restart journal`。第一版不上 CI，不上容器。
- 目录约定：代码 `/opt/journal`（只读），数据 `/var/lib/journal`（含 db、media、backups），两者分开，这样重装代码不会碰数据。
- 登录口令：部署时生成一个长随机串，只打印一次，写进服务器上的 `.env`（不进代码库）。

### 反馈怎么采集

第一版**不做显式打分**（让你给它的回复点个赞太累了，而且会破坏那种「随手说一句」的松弛感——一旦有了评分，你就开始为它的表现负责了。

代替方案是**弱信号**，只用来推断它的回复有没有用：
- 这条之后你有没有接着说（说了 = 它没把天聊死）
- 你有没有在 24 小时内继续这个话题
- 你有没有再点一次「问它」（说明上一轮没答到点上）

这些写进 `utterances.user_reaction`，**只用于调整它的开口频率和话题选择，不用来改它的语气**。语气是你定过的东西（「先问，再判断」），不该被数据悄悄改掉。

等用了几周、能看清哪些互动真的有效，再考虑要不要加显式反馈。

## 7. 我做的判断（你可以改）

这些是我替你决定的，列出来方便你检查：

1. **项目名 `journal`**，代码放 `/Users/admin/workspace/app/journal`。
2. **Python 而不是 Node** —— 服务器上 Python 已经装好了，少装一个运行时。
3. **SQLite 而不是 Postgres** —— 被 1.7 GB 内存逼的。
4. **不上向量检索** —— 数据量还不够，不值得。用 FTS5 够了。
5. **「记一笔」/「问它」两个按钮，而不是靠语义判断** —— 误判代价不对称。
6. **它不做心理诊断、不给抑郁风险评分** —— 见 5.6。这条我态度比较强，如果你不同意，我们得单独讨论。
7. **沉默信号只发极轻的招呼，且有上限和熔断** —— 见 5.3。
8. **第一版不做推送** —— 用户决定，代价见 5.8。
9. **一天的边界定在凌晨 4:00**。
10. **第一版不做 HTTPS 和 Tailscale** —— 为了不伤"随时能用"这条命。
11. **项目托管在 `github.com/lulukdog/journal`** —— ⚠️ 这个仓库目前是**公开的**，而本文档里有服务器公网 IP 和一句「root 弱口令」的风险记录。见文档末尾的安全提醒。
12. **状态分 `mood` 用 -2..+2，标签用你自己的话**，不用临床词。
13. **信号检测每晚只跑一次** —— 白天新增的记录只更新卡片，不即时触发判断，否则「重复」这类信号会在一天里被反复触发。
14. **记录先落库，模型不可用不影响记录** —— 记录功能失效比它说错话更致命。
15. **图片在浏览器端先压到长边 1568px** 再发给模型，原图仍然全精度存在服务器上。
16. **第一版不做显式反馈**，用弱信号推断。
17. **模型选择做成配置项**，不写死。

## 8. 安全提醒（关于这个仓库）

`github.com/lulukdog/journal` 目前是一个**公开仓库**（2026-10-13 核实，匿名可访问）。

而本文档里有两处不该出现在公开地方的内容：

1. **服务器公网 IP `39.96.68.27`** —— 配上第 3 节的端口信息，等于交出一个可直接扫描的目标。
2. **第 5.8 节那句「root + 弱口令 + 公网 22 端口」** —— 这句话等于告诉扫描器：那个目标值得爆破。

处理方式二选一：

- **推荐：把仓库改成私有。** 一条命令的事：
  ```
  gh repo edit lulukdog/journal --visibility private --accept-visibility-change-consequences
  ```

如果以后真想开源这个项目，正确做法是：把部署信息（IP、端口、口令）彻底从代码库里剥离，放进不进版本控制的 `.env`，文档里只保留占位符。
